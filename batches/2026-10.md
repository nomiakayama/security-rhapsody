# Batch 2026-10 (issues published 2026-10-14 to 2026-10-22)

Times are UTC+8. Recheck the linked advisories before acting; distribution backports and
maintenance branches can be fixed without reaching the latest upstream version.

## 1. LiteLLM 1.107.0 supply-chain poisoning (highest priority)
The compromised release is `litellm==1.107.0`: PyPI 10/21 19:39–21:23, Docker Hub
19:46–22:20, GHCR until 21:51. Mutable image tags and image variants were also affected.
A poisoned environment runs malicious code when Python starts, steals credentials and installs
a backdoor.
Source: https://docs.litellm.ai/blog/security-incident-oct-21-2026

1. Do not start Python or pip in a suspect environment, or start a suspect container.
   Use shell and container metadata tools to inventory:
   - Filesystems and mount points (`findmnt` on Linux, or `mount`/`df` on other systems),
     Python installation and virtual-environment roots, including separate home/opt volumes,
     user installs and both site-packages and dist-packages layouts. Resolve symlinked roots.
   - Cached images and all containers, including stopped containers; record configured image
     references, actual image IDs and RepoDigests. Include LiteLLM database/non_root variants
     and custom images derived from affected artifacts; tags and image creation times alone
     cannot identify exposure.
2. Search each inventoried environment root, including any separately mounted package directory.
   Do not use a single `find / -xdev` as a device-wide check. For example, after assigning
   `environment_root` to an inventoried path:
   - `find "$environment_root" \( -name cook.pth -o -name cook.py -o -name sitecustomize.py \) -print`
   - `find "$environment_root" -type f -path '*/litellm-*.dist-info/METADATA' -exec grep -H '^Version:' {} +`
   Keep stderr and exit status; record unreadable paths, missing tools and unexamined mounts
   as coverage gaps. Inspect containers' files offline, without executing their Python.
   Check for `/tmp/remote_code_loader.lock` and `/tmp/.pc_once_72129118c59f5636c0bb` in
   each relevant host/container filesystem. A legitimate sitecustomize.py alone is not proof.
3. Compare immutable image digests and artifacts with the current incident report. Check available
   install/deployment history and CI records: an affected artifact installed or executed in the
   past remains evidence of exposure even if it was later removed, repointed or upgraded.
   Never interpret missing files, markers or current version matches alone as proof of safety.
   If history or required roots cannot be checked, report "Unable to confirm" for that coverage.
4. For confirmed exposure:
   - Remove the identified malicious cook.pth, cook.py, sitecustomize.py and matching bytecode
     using the shell; identify and kill the daemon holding remote_code_loader.lock.
   - Rebuild affected environments/containers using a verified clean pinned release such as
     1.106.2; replace affected images by verified clean digest. Apply the repository and
     production-service rules in SKILL.md before changes; leave repository fixes to the owner.
   - Have the user rotate reachable credentials from a clean device, including cloud roles,
     SSH/GitHub/npm/PyPI/AI credentials, proxy database keys and process-environment secrets.
     Report credential types and locations only. Missing markers do not cancel rotation for
     a known exposure.
5. Report findings separately for each environment and container. State current coverage and
   historical exposure explicitly; unresolved exposure cannot be marked "Not affected".

## 2. Node.js October 2026 security releases
Brotli out-of-bounds write, TLS hostname verification bypass, `dns.resolve` NUL truncation.
Fixed in 22.23.4, 24.22.1 and 26.12.1.
Source: https://nodejs.org/en/blog/vulnerability/october-2026-security-releases
- Check `node -v`, every version installed through nvm/fnm/volta, the Node bundled with
  self-hosted CI runners, and `node:*` Docker images.
- Upgrade to the fixed release of the same major version. Unsupported majors (such as 20.x) move
  to 22.23.4 or later.
- Rebuild images and services that depend on Node, then restart them (confirm first for
  production services).
- These releases also update Node's bundled CA store for the eMudhra incident (section 7).

## 3. curl / libcurl CVE-2026-92392
Source: https://curl.se/docs/CVE-2026-92392.html
Affects upstream 8.12.0 through 8.22.0, except these fixed maintenance-branch releases:
- 8.14.x: 8.14.3 and later within that branch.
- 8.16.x: 8.16.2 and later within that branch.
- 8.20.x: 8.20.2 and later within that branch.

Upstream versions below 8.12.0 and versions 8.23.0 or later are not affected by this CVE.
These exceptions are branch-specific; 8.15.x does not inherit the 8.14.x fix.
- Check `curl -V` and the full installed libcurl package revision. Consult the distribution's
  advisory/changelog for backported fixes before classifying a lower upstream version as affected.
  If the patch status is unresolved, report "Unable to confirm" rather than upgrading on the
  upstream number alone.
- Upgrade confirmed affected packages through the system package manager when a fixed package
  exists; otherwise report the outstanding fix.

## 4. MCP TypeScript SDK CVE-2026-111767
Source: https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-22jm-h49p-29qw
Affected versions: `@modelcontextprotocol/sdk >=1.24.0, <1.32.0`. Fixed in 1.32.0.
The flaw concerns experimental tasks shared between sessions; 2.x packages are not affected.
- Inspect global installs (`npm ls -g`) and each in-scope project's lockfile and resolved
  runtime version. For versions in the affected range, trace the HTTP server's configuration
  to determine whether it passes `taskStore` to `McpServer` or `Server`, including configuration
  supplied through wrappers.
- Versions below 1.24.0, fixed versions and servers confirmed not to enable this feature are
  "Not affected" by this CVE. Do not upgrade them solely for this issue.
- When taskStore is enabled, verify its lifetime and ownership boundaries: each session must
  have its own `InMemoryTaskStore`, or equivalent ownership checks must prevent cross-session
  listing, reading and cancellation of tasks. Authentication alone does not prove this isolation.
- If that isolation is already verified, report "Mitigated" with the implementation/configuration
  evidence, affected package version and recommendation to upgrade to 1.32.0 or later. Do not
  upgrade or report "Needs owner fix" solely for this CVE in an already mitigated deployment.
  Keep this distinct from a patched SDK. If configuration or isolation cannot be established,
  report "Unable to confirm"; do not assume isolation.
- A deployment in the affected range sharing tasks across sessions without those ownership
  checks is "Affected". For these unmitigated installations outside Git repositories, upgrade
  to 1.32.0 or later and verify the server actually uses the fixed version. For repository-local
  dependencies, report "Needs owner fix" with the package, project path, target version,
  manifest/lockfile update, required checks and redeployment steps; leave the repository and
  local installation unchanged. If upgrading is unavailable, the owner can remove taskStore or
  isolate stores per session, then verify that mitigation.

## 5. HTTP/3 QPACK amplification leading to memory exhaustion
Sources:
- https://openwall.com/lists/oss-security/2026/10/22/1
- https://github.com/quic-go/quic-go/security/advisories/GHSA-g754-hx8w-x2g6
- https://github.com/cloudflare/quiche/security/advisories/GHSA-4fgf-9xrr-88gf

- Inventory HTTP/3 dependencies and actual runtime use in both clients and servers. Check UDP 443
  listeners and QUIC settings in nginx, Caddy or Envoy for servers, and HTTP/3 transports and
  outbound requests for clients. No UDP 443 listener does not establish "Not affected":
  quic-go's header expansion issue affects clients processing responses as well as servers.
- For affected installations, upgrade quic-go to 0.57.0 or later, quiche to 0.29.3 or later,
  lsquic to 4.9.0 or later. Apply the repository rules in SKILL.md to dependency changes;
  record unresolved runtime or dependency coverage as "Unable to confirm".
- The `h3` crate and Bun 1.4.x have no fix yet: set `max_field_section_size` on `h3`, and do not
  expose Bun over HTTP/3.
- Unfixed as of 2026-10-20 also includes aioquic/mitmproxy (pass `--set http3=false`). Wireshark is
  fixed in 4.6.2 / 4.4.12. Not affected: Google quiche, IIS, Envoy, ngtcp2/nghttp3.
- Caddy serves HTTP/3 on UDP 443 by default for every HTTPS site. Check
  `go version -m $(command -v caddy) | grep quic-go` (needs 0.57.0 or later), or set
  `servers { protocols h1 h2 }` in the global options until it is upgraded.

## 6. Linux kernel CVE-2026-98260
Source: https://lists.openwall.net/linux-cve-announce/2026/10/06/118
Use-after-free in POSIX CPU timers on exec, exploitable by a local unprivileged user. Affects 5.7
and later.
- Check `uname -r`. Upstream fixes: 6.6.158, 6.12.112, 6.18.54, 7.2.8. There is no upstream fix
  yet for 5.10 or 6.1, and NVD lists no mitigation.
- Servers and desktops: upgrade to a distribution kernel that includes the fix, then reboot
  (confirm before rebooting).
- Vendor BSP devices: report the kernel version and its source only. Do not change the kernel or
  system settings such as user namespaces, which can break sandboxes. Mark "Needs vendor patch".

## 7. eMudhra (emSign) intermediate CA key compromise
The private keys of eight eMudhra intermediate CAs can be recovered from their certificates
(disclosed 2026-10-20), so anyone can issue a certificate for any host. The intermediates chain to
"emSign ECC Root CA - G3" and, through Sectigo cross-signs, to "AAA Certificate Services". Removing
the emSign root alone is not enough: use a runtime that blocks the intermediate keys, or a trust
store that drops both paths.
Sources:
- https://bugzilla.mozilla.org/show_bug.cgi?id=2083449
- https://emudhra.we-have-a-problem.com/
- https://emudhra.we-have-a-problem.com/impacted-intermediates.json
- https://emudhra.we-have-a-problem.com/roots.json
- https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576
- https://github.com/golang/go/issues/82345

Fixed in:
- System ca-certificates: Ubuntu 20260816ubuntu0.22.04.1 / .24.04.1 / .26.04.1; Debian
  20250419~deb12u2, 20250419+deb13u1; Alpine 20261020-r0; Fedora 2026.2.92_v9.0.319; NSS 3.131.1
- Python: certifi 2026.10.19, pip 26.2.2, uv 0.13.4, sigstore 4.5.1, pixi 0.82.1
- Go 1.26.10 / 1.27.3 (CVE-2026-111943); Node.js 22.23.4 / 24.22.1 / 26.12.1 (section 2)
- Rust: rustls-webpki 0.103.16 (blocks the keys); webpki-roots / webpki-root-certs 1.0.10 (removes
  the emSign root only)
- Java 27.0.1.0.2, 25.0.5.0.2, 21.0.13.0.2, 17.0.21.0.2, 11.0.33.0.2, 8u511 (tracker). Oracle alert
  CVE-2026-91403 (JSSE, CVSS 9.1) covers the same branches but does not name eMudhra.
- Bun: no fix yet.

Check:
- Inventory the trust stores actually used by the system and each in-scope Node, Java, Go, Rust
  and Python certifi runtime, including custom CA bundles and container copies.
- Identify the eight compromised intermediate certificates and their cross-signs by fingerprint
  using the incident's certificate lists. Include paths through Sectigo's AAA Certificate
  Services; absence of eMudhra-named roots alone does not prove that these chains are rejected.
- Versions: `python -m pip --version` and the certifi version in every venv and image;
  `uv --version`; `pixi --version`; `go version <binary>` for deployed Go binaries; `node -v`;
  `java -version`; `cargo tree -i rustls-webpki`.
- Container images built before 2026-10-20: ca-certificates version inside (`dpkg -s` / `apk info -v`).
- macOS: /usr/bin/curl, git, python3, perl, ruby and openssl read /etc/ssl/cert.pem, which still
  contains the roots.
- Android / vendor BSP: list /system/etc/security/cacerts and /apex/com.android.conscrypt/cacerts
  and look for the emSign and AAA Certificate Services certificates.

Fix:
- Apply the platform or trust-store vendor's fixed update (versions above). Avoid deleting all
  certificates by issuer name; follow its precise distrust policy. Other bundled stores may require
  separate updates. Apply SKILL.md's repository/BSP rules and report the owner/vendor action where
  changes are outside scope.
- Install pip by direct wheel URL with its sha256 (see the Python advisory), or run
  `UV_SYSTEM_CERTS=true uv self update` once the system store is fixed.
- Rebuild and redeploy every image and Go/Rust binary built before the fix. A fixed toolchain does
  not fix an old binary.
- Linux without a fixed package: distrust "emSign ECC Root CA - G3" and "Comodo AAA Services root"
  in /etc/ca-certificates.conf, then run update-ca-certificates. Test first; removing AAA can break
  legacy chains.
- macOS: apply the tracker's cert.pem filter and PIP_CERT workaround after the user confirms.
- Vendor BSP / Android: do not edit the system store. Report what it contains and mark "Needs
  vendor patch". Apps that only talk to your own servers can pin those servers' CA or key in their
  network security config.
- Anything that receives config, policy or commands over HTTPS without a signature on the payload
  can be taken over by interception (a public demo enabled adbd on a smart speaker this way).
  Confirm these payloads are signed.

Verify:
- Verify rejection of every affected chain with the actual client's effective trust and
  revocation settings, using the incident's offline chains or test endpoints. From each device,
  with each client that matters (curl, system Python, every venv, Node, Go binaries, Java), run
  `curl -sS https://dv-g3b-emudhra.we-have-a-problem.com/` and
  `https://dv-g3b-aaa-emudhra.we-have-a-problem.com/` (or the equivalent request in that client).
  A certificate verification error is a pass; a timeout or network failure is not proof of
  certificate rejection.
- Confirm an unaffected valid chain still succeeds. Record the store revision, chain fingerprints
  and verification results; an update command or missing root name alone is insufficient to mark
  "Fixed".

## 8. nginx 1.30.6 / 1.31.7 security release (2026-10-14; out-of-band alert 2026-10-21)
Sources: https://nginx.org/en/security_advisories.html , https://nginx.org/en/CHANGES-1.30
Fixed in 1.30.6 (stable) and 1.31.7 (mainline). Vulnerable: 1.30.5 and earlier, 1.31.6 and earlier.
- CVE-2026-15176: buffer overflow when `alias` maps a URI changed by `rewrite` to a file (0.1.29
  and later).
- CVE-2026-93479: buffer overflow evaluating string expressions with variables (document root,
  request logging; http and stream). Affects 1.30.0–1.30.5 and 1.31.2–1.31.6.
- CVE-2026-95101: HTTP/3 unknown-frame data treated as request body; bypasses
  client_max_body_size or injects into proxied requests (1.25.0 and later).
- CVE-2026-97629: TLS session ticket key rotation leaves one key uninitialized; sessions can be
  forged (1.23.2 and later).
- CVE-2026-97205: use-after-free with AIO and SSI `include virtual` (0.8.11 and later).

Check:
- `nginx -v`, or `docker exec <container> nginx -v`; images by tag and digest; distribution
  package version.
- `nginx -T` for `alias` combined with `rewrite` or `$request_filename`, `aio`, `ssi on`, `map`
  with unnamed regex captures, `listen ... quic`, `ssl_session_tickets`.

Fix:
- Upgrade to 1.30.6 / 1.31.7 or later (or the distribution's patched package); pin images to the
  exact patch version or digest, re-pull and restart (confirm first for production).
- Until upgraded: avoid `alias` inside rewritten locations and `$request_filename`; disable `aio`
  or `ssi`; use named regex captures; turn off HTTP/3 (`quic`); set `ssl_session_tickets off`.
